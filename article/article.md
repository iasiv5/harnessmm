# Agent 已经决定的下一步，为什么还要再想一次？——一次 HarnessMM 机制复现实验

> 本文是一次真实运行的机制复现记录。实验于 2026-11-03 在本机完成，模型为 GLM（glm-5.3-flash）。
> 正式运行的 27 次模型调用（修复 16 + R1 5 + R2 3 + R3 3）与开发运行的 29 次调用全部为
> 真实 API 调用，账本数字全部来自供应商实测 usage。项目定位是**机制复现**
> （mechanism demonstration），不是论文完整复现，也不做普遍性能声明。

---

## 1. 问题：工具返回之后，为什么又要调用模型？

主流 Agent harness 的循环是"模型决定 → 工具执行 → 结果回喂 → 模型再决定"。注意第二步到第三步：
每当工具返回，harness 默认把回执塞回上下文、再调用一次推理模型，哪怕这次回执只是确认了一件
**模型早就决定好的事**。

一个典型的验证链是这样的：修完代码后，"跑单元测试 → 跑集成测试 → 构建产物 → 校验产物"这四个
动作及其完整参数，在第一条命令执行之前就已经完全确定了——没有哪个参数需要等前一条命令的输出才能
填写。可是按默认循环，每条命令返回后模型都要被重新调用一次，重新"想一想"下一步。

论文《HarnessMM: Recursive Self-Improvement for Harness Token Efficiency》
（[arXiv:2610.32813v1](https://arxiv.org/html/2610.32813v1)，§1）把这类情况命名为
**已解决决策（resolved decision）**：先前的推理已经固定了动作和字面参数，未知的只是工具回执；
回执的作用是**激活**这个决策，而不是重新生成它。

本文记录我们如何用一个小到可以逐行读懂的任务，把这套机制真实跑起来：哪些判断提前完成了、
工具反馈如何约束后续执行、哪些模型调用确实没有发生、什么时候系统必须重新交给模型。

## 2. 论文机制：决策、反馈检查和回调替代如何分工

论文的核心是三个组件（以下为论文原文主张，标注章节位置）：

| 组件 | 论文定义 | 出处 |
|---|---|---|
| **EDG**（Executable Decision Graphs，可执行决策图） | 慢推理在一次决策中，除当前动作外还产出一张有界延续图。每个未来节点是四元组 `(a_j, arg_j, pred_j, g_j)`：原生动作、**完整字面参数**、前置节点、公共守卫。守卫在创作时固定，由适配器对照后续**真实回执**求值。 | §4.1，式(4) |
| **GDR**（Guarded Decision Reuse，守卫式决策复用） | 图**跨工具转移保留**。资格判定 = 前置完成 ∧ 守卫为真 ∧ 参数封闭。守卫只消费已观察回执、从不消费预测结果；不支持的观察、未满足的依赖、需要新推理的参数，一律交还慢路径。 | §4.2，式(5) |
| **CCS**（Certified Callback Substitution，认证回调替代） | 已入场的决策直接走 `s_t → d_j → a_t`，**跳过**原本的 `s_t → H_0 → a_t` 慢调用，经原始工具接口执行。每 次 替 代 绑 定 证 书 `(graph_hash, decision_id, predecessor_receipt, exact_args, tool_receipt, bypassed_callback_id)`，审计要求被跳过的边界**没有对应模型请求**。 | §4.3，式(6)(7) |

论文还强调两件事，直接影响本项目的记账方式。其一，**替代悖论**（§3.3）：只有被消除的推理大于
新增的创作、选择与恢复成本时才真正省钱，因此记账必须包含图创作、选择器、回退和失败执行的
全部成本（§4.4）。其二，**守卫通过 ≠ 任务正确**（§4.2）："先前的推理是否正确解决了该动作"
是语义假设，由任务评分评估；守卫只证明其声明的公共条件成立。

## 3. 实验边界：复现什么，不复现什么

**复现的**：任务内执行机制——决策提前生成（EDG）、跨反馈保留与守卫检查（GDR）、
回调替代及其证书（CCS）、守卫失败/条件不明/工作区变更时的回退。

**不复现的**：论文的递归自我改进（RSI，§5.6——那是任务外配置优化，与任务内执行分离归因）、
提示词自动优化、上下文压缩、类型化模型选择器（我们用公开的确定性规则代替）、
以及任何跨任务泛化声明。

**与论文的差异全部是显式教学简化**，逐条记录在
[`docs/paper_mapping.md`](../docs/paper_mapping.md)：选择器简化、守卫表达受限、单任务、
故障注入是人为装置、R1 的"每步一动作"是实验控制。论文报告的数字（HumanEval 29.54% 节省等，
§5.3）只是论文主张，与本项目无关——尽管下文会有一处数字巧合，我们会明确指出它是巧合。

## 4. 教学任务与共同检查点

任务是一个约 80 行的 Python 配置解析器（人为构造的教学项目，不是真实内部项目）：

```
修复配置解析器，使其同时支持十进制和 0x 前缀的十六进制端口号。
保持既有非法输入校验规则不变。完成单元测试、集成测试、产物生成与产物校验，最后报告结果。
```

初始代码**真的有 bug**：`parse_port` 只接受纯十进制，`"0x1F90"` 被拒（初始状态实测：
单元测试 7 failed / 20 passed，集成测试 2 failed / 3 passed，产物校验 FAIL——失败模式恰好
锁定在十六进制能力上，非法输入规则完好）。

验证链四步，全部真实可运行：

```bash
python -m pytest tests/unit -q                                    # N1
python -m pytest tests/integration -q                             # N2
python tools/build_artifact.py --out dist/package.zip             # N3
python tools/verify_artifact.py --file dist/package.zip           # N4
```

其中 N4 不是"检查文件存在"：它解压产物、核对 manifest 里每个文件的 sha256、
再从产物内提取解析器**真实导入**并执行 12 个行为样例（十进制、十六进制、非法输入）。
独立评分器（[`tools/scorer.py`](../tools/scorer.py)）另有三重保险：受保护文件
（tests/、tools/、server.conf）哈希防篡改、四步全链重跑、以及一套**评分器自带的**
独立测试向量直接测工作区解析器——被测模型改测试文件无法"通过"。
参考答案放在模型不可见的 `reference/` 目录，不作为工具暴露。

**实验流程**：先用真实模型修复 bug（被测模型通过白名单工具读写工作区），
评分器通过后保存共同检查点 C0（工作区快照 + 对话历史 + 成本前缀 + 环境版本）。
三条验证臂全部从同一个 C0 出发，各自使用独立的工作区副本、相同的模型与解码设置
（glm-5.3-flash，temperature 0.1，思考关闭）、相同的工具白名单、相同的全历史上下文策略、
相同的评分器。模式间唯一允许的差异是验证协议本身（R1 单步 vs R2/R3 决策图）。

## 5. 两条正常轨迹：逐步回调 vs 持续决策图

### R1：逐步回调基线（受控协议）

R1 的协议是**实验控制**：每次回复只允许提交一个独立验证动作，收到回执后才能决定下一步。
这不是普通 Agent 的能力上限（普通 Agent 完全可以合并命令），它是为了给"每步都问模型"的
默认循环一个公平的、可量测的形态。

正式运行（`runs/formal-1/arm_r1`）中，模型的五次决策依次是：

```
req-001  跑单元测试        {"thought": "验证阶段第一步：重跑单元测试确认当前工作区状态。", ...}
req-002  跑集成测试
req-003  构建产物
req-004  校验产物
req-005  phase_complete + 总结
```

五次调用，**四条命令**——每个工具返回之后，都要再想一次。

### R2：持续决策图与回调替代

R2 从同一个检查点出发。模型的第一响应同时包含当前动作和一张图
（[`runs/formal-1/arm_r2/graphs/verify-formal-1.json`](../runs/formal-1/arm_r2/graphs/verify-formal-1.json)）：
三个未来节点，参数是**逐字节完整的字面 argv**，链式依赖，每个节点带守卫（如 `{"exit_code": 0}`）。

之后发生的事情是这次实验的核心画面：

```
seq 2  MODEL_REQUEST  模型创作（当前动作 + 图，唯一一次"想"验证链）
seq 4  GRAPH_AUTHORED 图已保存（绑定创作请求 ID 与工作区哈希）
seq 6  BYPASS n1      集成测试自动执行，exit=0，无模型请求
seq 8  BYPASS n2      构建自动执行，exit=0，无模型请求
seq 9  INVALIDATED    n3 守卫失败（详见第 6 节）
seq 10 MODEL_REQUEST  回退：模型带真实回执重新决策
seq 12 MODEL_REQUEST  最终总结
```

两条轨迹回答了同一个问题的两种答案：R1 每一步都调用模型（5 次）；
R2 把"已经决定的"存下来，让回执去激活它们（图内的执行零调用），只有新语义判断才回到模型。

## 6. 放大关键边界：下一步早已决定，反馈只是确认条件

R2 的正式运行里出现了一个**计划之外、但恰好在设计之内**的事件，它把机制的关键边界展示得
比顺利版本更清楚。

模型创作的图中，校验节点 n3 的守卫写的是 `{"exit_code": 0, "stdout_contains": "PASS"}`。
运行时执行完 n2（构建）后，对照**前置回执**（构建的输出是 `BUILD OK: ...`）求值守卫——
构建输出当然不含 "PASS"。运行时没有猜测模型意图、没有静默修正守卫，而是：

```
seq 9  graph_invalidated  guard_failed at n3: exit_code==0 ok; stdout does not contain 'PASS'
```

剩余图作废，控制权带着真实回执交回模型。模型自己重跑了校验命令（`ARTIFACT VERIFY: PASS`，
exit=0），确认四步全部真实通过后才宣布完成。它甚至总结道"此前守卫失败应属误判"——
从机制视角看这不是误判，而是运行时诚实地执行了一条**语义写错的守卫**：guard 的求值对象是
前置回执，"PASS"出现在校验命令自己的输出里，而不是它前置的构建输出里。

这一段留下两个可复核的事实。第一，**执行参数与保存决策逐字节一致**（审计第 2 项：
`authored_args_hash == executed_args_hash`，由图文件重算核对）。第二，**条件只消费已观察的
真实回执**（审计第 3 项：审计器从回执文件重算守卫，与运行时判定一致）。
"下一步早已决定"和"反馈约束执行"在这里同时成立：决定好的照常执行，写错的条件被真实回执拦下。

## 7. 故意失败：下游阻断与模型回退

R3 与 R2 用同一套实现，但工具层在集成测试命令上注入一次**真实失败**：环境变量
`HARNESSMM_FAULT_INJECT=integration` 让 `tests/integration/test_environment_probe.py`
真实断言失败、pytest 真实退出非零（一次性触发、全程显式标注为教学装置）。
这不是论文机制的一部分，是为了观察"故障后系统做什么"而人为构造的路径。

正式运行（`runs/formal-1/arm_r3`）的完整叙事：

```
seq 4  GRAPH_AUTHORED  verify-chain-r3（3 节点）
seq 5  FAULT_INJECTED  inj-formal-1-arm_r3-1
seq 7  BYPASS n2       集成测试自动执行，exit=1（真实失败，回执含注入标注）
seq 8  INVALIDATED     guard_failed at n3: exit_code got 1, guard wants 0
                       —— 下游构建/校验节点没有被自动执行
seq 9  MODEL_REQUEST   回退：真实调用，附真实失败回执
seq 11 GRAPH_AUTHORED  verify-chain-r3-retry（新图，明确区别于原图自动继续）
seq 13 BYPASS n3       重试后的构建自动执行，exit=0（注入已解除）
seq 15 BYPASS n4       校验自动执行，exit=0，输出 ARTIFACT VERIFY: PASS
seq 17 MODEL_REQUEST   最终总结；评分器 exit=0
```

三个机制事件同时被证据锁定：**下游阻断**（审计第 7 项：故障后原图没有任何新节点自动执行，
唯一例外的"受害者"节点正是记录注入失败的证书本身）；**回退产生真实请求**（审计第 8 项）；
**重试与原图继续明确区分**（重试是新的 `graph_id`、新的创作请求，事件流一目了然）。

## 8. 实测结果：调用、Token、任务结果和审计

正式运行 `runs/formal-1`，模型 glm-5.3-flash（temperature 0.1，思考关闭），
每臂预算上限 16 次调用（远未触顶），全部调用经统一入口
（[`harness/llm.py`](../harness/llm.py)），usage 为供应商实测值。

### 共同修复阶段（三条臂共享的前缀）

模型修复 bug 用了 **16 次调用**（输入 38,300 / 输出 2,714 tokens），
期间仅 1 次工具拒绝回退（模型记错测试文件名，被白名单拒绝后自行纠正）。
修复完成后评分器 PASS，保存检查点 C0。

### 三条验证臂（从同一检查点出发）

| 指标 | R1 逐步回调 | R2 决策图 | R3 故障注入 |
|---|---|---|---|
| 本臂模型调用 | 5 | 3 | 3 |
| 本臂 tokens（输入/输出） | 27,078 / 352 | 18,666 / 665 | 19,413 / 681 |
| 本臂 tokens 合计 | 27,430 | 19,331 | 20,094 |
| CCS bypass（无模型请求的执行） | **0** | **2** | **3** |
| 图创作 / 失效 | 0 / 0 | 1 / 1 | 2 / 1 |
| 注入故障 | 0 | 0 | 1 |
| 执行的验证命令数 | 4 | 4 | 5（含故障重试） |
| 独立评分器 | PASS | PASS | PASS |
| 结构审计（10 项检查） | PASS | PASS | PASS |

含共同前缀的口径（共享前缀只列示、不重复计入结论，见
[`runs/formal-1/results.md`](../runs/formal-1/results.md)）：R1 = 21 次调用 / 68,444 tokens，
R2 = 19 次 / 60,345，R3 = 19 次 / 61,108。

### 怎么读这张表

**机制判据全部满足**（这是本项目的主要成功标准，成本次之）：
同一图跨反馈连续执行多个节点（R2 的 n1→n2，R3 重试图的 n3→n4）；执行参数与保存决策哈希一致；
每次直接执行都有前置回执守卫；请求账本证明 bypass 边界没有任何模型请求
（审计第 6 项：模型事件 ID 集合与账本一一对应）；故障阻断下游并回退；回放由事件重新生成
（审计第 10 项：回放内嵌事件文件 sha256 核验一致）。

**调用与 token 在本次运行中确实下降了**：R2 本臂调用 5→3、tokens 27,430→19,331（↓29.6%）。
但有三点必须说清。第一，**这个 29.6% 与论文的 29.54% 是数字巧合**——总体、任务、协议、
成本口径全都不同，不构成任何相互印证。第二，下降的直接原因是**调用次数减少**
（每省一次调用就省掉一次重复回放的历史输入），而 R2 多付出的部分是图创作的输出与协议开销；
R2 的第三次调用恰恰来自一次守卫失败回退，换言之这次运行里"回退税"已经计入了。第三，
**缓存命中差异很大**（R1 缓存命中 16,640 tokens，R2 只有 7,360），不同 harness 策略会显著
改变供应商记账，"节省"结论对记账方式敏感——论文自己在局限节也承认这一点（§6）。

**"模型未调用"没有折算成任何金额**。bypass 是一个事实陈述：该边界上没有请求记录。
我们没有供应商单价，也不编造费用；token 数字全部是供应商实测 usage
（含 `cached_tokens` 与 `reasoning_tokens` 字段的逐请求明细，
见 [`runs/formal-1/arm_r2/ledger.jsonl`](../runs/formal-1/arm_r2/ledger.jsonl)）。

**单任务、单次运行**。以上数字只说明"这套机制在这个任务上按预期运转"，
不说明它普遍省 token，也不说明 R2 优于 R1——那需要多任务、多重复、有统计基础的对照，
本项目明确不做此声明。

## 9. 为什么不直接写脚本？

诚实的回答分三层。

第一层：**这个任务的验证链当然可以直接写脚本**。四条命令、参数固定、顺序固定——
`pytest && pytest && build && verify` 一行 shell 就够了，而且更简单。我们从头到尾不声称
决策图在这个任务上"优于"脚本；EDG 的价值假设是"参数在反馈前已确定"的决策可以被安全地
**保存和复用**，而不是"凡事都该预先图化"。论文的适用条件（§6）同样如此：节省取决于
已解决动作的可得性。

第二层：**脚本是这份对比里被隐去的第三臂**。HarnessMM 回答的不是"要不要自动化"，
而是"当 harness 已经由模型驱动时，重复的推理调用能否在不损失能力的前提下被省掉"。
它的对照对象是"每步都问模型"的循环（R1），不是人类写死的脚本。把受控 R1 说成
"普通 Agent 的上限"是错误解读——这正是我们公开全部控制条件的原因。

第三层：**机制复现关心的是可观察的事件，不是端到端的最好成绩**。固定流程可以直接脚本化，
这恰恰说明 EDG 复用了"本可以脚本化"的决策——但脚本没有回答"哪些判断是模型提前完成的、
运行时凭什么敢不问模型、什么时候必须交还"。本项目的事件账本回答的就是这些问题。

## 10. 局限与结论

**局限**（全部公开，详见 [`docs/paper_mapping.md`](../docs/paper_mapping.md) §5–6）：
单任务、单次正式运行，无泛化声明；R1 的每步一动作是人为控制；选择器是确定性规则而非模型；
守卫只支持三种受限检查；故障注入是教学装置；缓存与记账口径影响成本对比；
R2 样本里唯一的图失效恰好演示了机制，但也让"顺利情形"的成本看起来比 dev 运行
（2 次调用）更贵——两次运行都保留在 [`runs/`](../runs/) 下，选择规则见下节。

**结论**：在一个人为构造但完全真实的小任务上，HarnessMM 的任务内执行机制——
决策提前生成、跨反馈保留、守卫约束下的回调替代、异常时回退——按论文描述的方式运转，
且每个环节都有可复核的记录。被省掉的模型调用是**事实**（账本里不存在的请求），
