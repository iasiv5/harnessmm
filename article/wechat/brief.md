# Brief：公众号文章《Agent 的下一步早就想好了，为什么还要再想一次？》

## 读者起点

读者是关注 AI coding / agent 工程的公众号订阅者：知道 Agent、Prompt、Token 是什么，
自己可能正被 agent 的 token 账单或"工具每返回一次模型就想一次"的等待时间困扰；
没读过 HarnessMM 论文，不了解 harness 内部的调用循环。
读者此刻已在关心：token 账单怎么降、agent 慢在哪、harness 工程还有没有油水。

## 入口方案（比较两个）

- 入口 A（选它）：研究断言式开场——"模型越来越强，harness 应该越来越薄"，接
  HarnessMM = Harness 减减 的名字巧合，再落到"我们照着论文做了个实验"。
  与作者过往 Harness 马具比喻（20260617 演讲稿）自然衔接，读者群熟悉这条线。
- 入口 B（弃）：从论文摘要开始介绍机制。弃因：像论文导读，读者要叠两个前提
  （知道这篇论文 + 关心论文）才会被吸引，超过两项前提即换入口。

## Thesis（一句话、可证伪）

Agent 每次工具返回后都重新调用模型，其中一部分"想"其实早就完成了；
我们照着 HarnessMM 论文做的小实验证明：把已经确定的下一步存下来、让工具回执去激活它，
真实调用次数和 Token 都能降下来，而且写错条件或故意灌失败时，系统会正确地交还控制权。

## 信息增量

亲手复现的一手证据（别人转述论文没有）；复现中暴露的机制边界（守卫写错被运行时拦截，
这是论文正文不会给你看的画面）；面向开放 agent runtime 的落地路径。

## 单一带走点

"模型调用是可以省的，省的方法是把已确定的决策存下来、用真实回执去激活它；
省不掉的部分——新判断和异常处理——必须老老实实交回模型。"

## H2 规划（问题驱动，共 8 节，正文目标 1800–2300 字）

1. 「为什么工具返回之后，模型还要再想一次？」（~300 字）
   痛点场景开场：验证链四条命令，参数早就确定，默认循环却要模型想四次。
   接读者关心的账单与等待时间。
2. 「HarnessMM 的主意：想好了就写下来」（~350 字）
   论文依据声明（清华大学与 MSRA 作者，arXiv 链接）；HarnessMM = Harness 减减；
   用"任务备忘录 + 完成条件"白话讲 EDG/GDR/CCS；明确这是任务内机制，不是模型训练。
3. 「我搭了个最小实验」（~350 字）
   80 行解析器任务、四步验证链、三条臂为什么这么设（R1=每步都问的基线，R2=存决策，
   R3=故意灌失败）。配图 1（实验设定示意）。声明：教学任务、不证泛化。
4. 「同样的四条命令：5 次调用 vs 3 次」（~400 字）
   R1 逐条决策实录 vs R2 一次提交决策图、图内执行零调用。配图 2（调用对比）。
   数字：R1 27,430 vs R2 19,331 tokens（↓29.6%），声明与论文 29.54% 是巧合。
5. 「最有意思的翻车：模型把守卫写错了」（~300 字）
   PASS 守卫写错位置 → 运行时拦下 → 回退 → 模型自查恢复。讲清"守卫只对照真实回执"。
6. 「故意灌一个失败进去」（~250 字）
   R3：真实失败 → 下游阻断 → 图失效 → 模型重试成功。配图 3（回放截图）。
7. 「数字、口径和边界」（~250 字）
   表格：三臂调用/token/bypass/审计。缓存差异、共享前缀、单任务不泛化、无金额折算。
8. 「后记：这套东西能落到哪」（~300 字）
   展望：DeepSeek 开放 agent runtime 上做 callback 级拦截；哪些循环值得先做；
   与 RSI 的距离。结尾：残留问题 + 评论区提问 + GitHub 仓库链接。
