# Agent 的下一步早就想好了，为什么还要再想一次？

## 四条命令，模型要想四次

你让 Agent 跑一条验证链：单元测试、集成测试、构建、产物校验，四条命令，参数上一轮就定死了。按默认循环，工具每返回一次，模型都要再想一次下一步，四条命令要想四次。每一次“想”都是真金白银的 Token。

模型外面套着管调用循环的那层工程，统称 Harness，词源是马具：缰绳加笼头。我的判断：工具返回后这次“再想”可以省，但不能省到失控，下面用一次真实实验说话。

## HarnessMM 的主意：想好了就写下来

论文 “HarnessMM: Recursive Self-Improvement for Harness Token Efficiency”（[arXiv:2610.32813](https://arxiv.org/html/2610.32813v1)）讲的就是 Harness 减减，论文报告它已在 DeepSeek Harness 上省了 87.93% 的 Tokens/task；标题里的 Recursive Self-Improvement 是论文的另一部分，这次实验只做“把确定的决策存下来复用”这半个。

机制用白话讲分两步。第一步，模型在某次决策时除了交出当前动作，再把已经确定的下一步写成一张“决策清单”：用什么命令、参数是什么、顺序如何，每步带一个完成条件，后文叫守卫。清单落盘，交给运行时接管，就是 harness 里编排调用的那段代码。

第二步，工具跑完，真实的输出和退出码先回到运行时手里，它拿真实回执逐条对照守卫：满足，就直接执行那一步，省掉那次模型调用；守卫不满足、出了清单没料到的状况，控制权交回模型。清单由模型自己写，运行时从不替模型预测结果，整套机制发生在任务内，模型参数一个没动。

## 我搭了个最小实验

任务：修复一个约 80 行的 Python 配置解析器，初始版本只认十进制端口，输入 `0x1F90` 直接报错，起点是一批跑不过的测试。模型 glm-5.3-flash，全部真实 API 调用；先用 16 次调用修完 bug、评分器 PASS、存下检查点。三条路线从这里各自出发：R1 还原默认循环，每一步都让模型重新决定；R2 把四步验证写成决策清单，交给运行时；R3 在 R2 的基础上往工具层灌一次真实失败，专看出错怎么办。边界一句：教学任务，只演示这套机制怎么运转，不证明它能推广。

## 同样的四条命令：5 次调用 vs 3 次

R1 每一步都真的想一遍：第 1 次决定跑单元测试，回执回来再想一次跑集成测试，再想一次构建，再想一次校验，第 5 次写完成总结，四条命令 5 次调用、27,430 tokens。R2 换了做法：第 1 次调用提交当前动作，外加一张 3 节点的决策清单，当前动作不占位，后面的三步才进清单，之后清单节点由运行时对照真实回执激活执行，零模型调用。整条路线 3 次调用、19,331 tokens，开头交清单、收尾写总结，中间那次是下一节的翻车回退。

同样的检查点、同样的四条命令，调用 5 次 → 3 次，token 27,430 → 19,331，降 29.6%，这个数字与论文在另一套任务上报告的 29.54% 接近，纯属巧合，不作数。省掉的模型调用在账本里叫 bypass：运行时没经过模型、直接替模型执行的那几步，每次替代都留下可核对的执行记录。

## 两个意外

第一个意外是模型自己把守卫写错了：它给一个构建前置节点配的守卫是 stdout 包含 `PASS`，这个节点的真实回执是 `BUILD OK`。运行时逐字对照真实回执，判定守卫失败，剩余清单当场失效，控制权交回模型；模型自查后重跑校验，确认 `ARTIFACT VERIFY: PASS`，补上新判断后完成。守卫写错不会被悄悄放行，运行时会当场拦下。

第二个意外是故意灌的：R3 往工具层注入一次真实失败，pytest 以真实退出码 1 挂掉。这次失败阻断了下游的构建和校验节点，整张清单作废，运行时真实调用模型，没有 bypass；模型在新清单上重试成功，其余节点随后自动执行。整条路线 3 次调用、20,094 tokens、3 次 bypass，构成是 1 次故障节点的自动执行加 2 次重试成功后的构建和校验。

![R3 故障注入后的只读回放](../docs/assets/replay_r3.png)

## 数字和口径

修 bug 的 16 次调用是三条路线共用的开销，表里只算各路线自己的账。

| 路线 | 模型调用 | 本路线 Token | Bypass | 审计 |
|---|---|---|---|---|
| R1 每步回调 | 5 | 27,430 | 0 | 通过 |
| R2 决策清单 | 3 | 19,331 | 2 | 通过 |
| R3 故障注入 | 3 | 20,094 | 3 | 通过 |

审计是十项机器可查的检查，归成三类：执行参数和存档决策一致、环节记录对得上、故障后没有偷偷继续跑。各家缓存记账方式不一样，正文只算 token 总量，不折算成钱；这是单个任务的结果，别急着推广。

## 后记：这套东西能落到哪

以下是推演，我自己的判断，没实测过。开放 agent runtime 的价值在调用入口可拦截：入口先查决策清单，命中就替代，未命中放行；先做那些下一步早就定死的环节，比如跑测试、构建、部署，要读新信息做判断的调用省不掉。

更近的一步是把它做成 DeepSeek Harness（DSH）的插件：它的 slogan 是 “everything is plugin”，我最近在 DSH 上做的插件系统、模型登录界面、skill 的 bundle 都靠这套机制搭起来。把决策清单拦截器做成一个 DSH 插件，装在调用入口上，原生 DSH 的 token efficiency 就能直接受益。

具体结论一句：模型调用可以省，省法是把已确定的决策存下来、用真实回执去激活，省不掉的部分老老实实交回模型。你在用 Agent 时，哪段循环让你觉得“这步不用再问模型”？评论区聊聊。完整运行记录、事件账本、审计脚本都在 github.com/iasiv5/harnessmm 里。
