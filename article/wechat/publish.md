# Agent 早就想好了下一步，为什么还要再问一遍模型？

> 模型越来越强，Harness 应该越来越薄。清华和微软亚研的一篇新论文，名字就叫 HarnessMM，意思是 Harness 减减。我照着它搭了个最小实验，用真实调用记录看一看：Agent 每一步都回头问模型，到底有多少次是白问。

## 一、Agent 在为确定的事反复付费

你大概每天都见过这样的场景：让 Agent 跑一条验证链，依次是单元测试、集成测试、构建和产物校验。四条命令的参数，在上一轮就已经定死了。

默认的 Agent 循环却不管这些。工具每返回一次，结果就塞回上下文，模型再判断一次下一步该做什么，**四条命令要问四次模型**。每问一次，整段历史都要重新喂一遍，花的是真金白银的 Token，耗的是你盯着屏幕等待的时间。

套在模型外面、管这套调用循环的工程，统称 Harness，这个词原本指马具，就是缰绳和笼头。我一直觉得，**模型越强，Harness 就应该越薄**。模型已经想清楚的事，Harness 不该逼它再想一遍。

## 二、HarnessMM：想好了，就写下来

最近读到的这篇论文叫 [HarnessMM: Recursive Self-Improvement for Harness Token Efficiency](https://arxiv.org/html/2610.32813v1)，作者来自清华大学和微软亚洲研究院。MM 是 Minus Minus，也就是 Harness 减减，和我的想法正好撞上，于是我照着它做了这次实验。

论文报告，这套方法在 HumanEval 编程题上，帮 DeepSeek Harness 把每个任务的 Token 消耗降了 87.93%。论文标题里还有一半讲的是递归自我改进，这次实验没有碰，只复现了另一半：把已经确定的决策存下来反复用。

这个机制分两步走。

**第一步，写清单。** 模型在交出当前动作的这一轮里，顺手把后面已经确定的几步也写下来，包括用什么命令、参数是什么、谁先谁后，每一步再配一个完成条件，论文管它叫守卫。

**第二步，对答案。** 工具跑完后，真实的输出和退出码先回到 Harness 手里，由 Harness 逐条对照守卫。对上了，就直接执行清单里的下一步，**这一次模型调用就省掉了**；对不上，或者出现清单没料到的情况，控制权马上交回模型。

整个过程有两条底线：清单由模型自己写，Harness 不替它猜；守卫只认工具真实跑出来的结果，不认预测。

## 三、一个 80 行的最小实验

实验任务是修一个约 80 行的 Python 配置解析器。原版只认十进制端口，输入 `0x1F90` 就报错，一批测试跑不过。

模型用的是 glm-5.3-flash，**所有调用都是真实 API 调用**，Token 数字全部取自供应商返回的账单。模型先用 16 次调用修好 bug，独立评分器复核通过后，我存了一个检查点，再从这个检查点出发，用三种方式跑同一条验证链：

- **R1 每步回调**：还原默认循环，每跑完一条命令都问一次模型
- **R2 决策清单**：模型一次写好后续清单，Harness 对照真实结果自动执行
- **R3 故障注入**：和 R2 一样，但我在工具层故意制造一次真实失败，看系统怎么收场

![实验怎么设计的](../docs/assets/wx_setup.png)

这是一个教学任务，只用来演示机制怎么运转，单个任务的数字不能推广到别处。

## 四、同样四条命令：5 次调用 vs 3 次

**R1 老老实实问了 5 次。** 第 1 次决定跑单元测试，结果回来后再问一次跑集成测试，接着问构建、问校验，第 5 次写总结，合计 27,430 Token。

**R2 只问了 3 次。** 第 1 次调用时，模型交出当前动作，外加一张 3 步的决策清单。之后的集成测试和构建，Harness 对照结果直接执行，没有经过模型。最后一次调用写总结，中间多出的一次，是下一节要讲的翻车，合计 19,331 Token。

![同样四条命令，要问模型几次](../docs/assets/wx_calls.png)

两相对比，**调用从 5 次降到 3 次，Token 降了 29.6%**。论文在另一组对比里报告过 29.54%，两个数字接近纯属巧合，任务和统计口径都不一样，不能互相印证。

省掉的那几次调用，在账本里叫 bypass，指 Harness 没问模型、直接替它执行的步骤。每次 bypass 都留有可核对的记录，账本里也查不到对应的模型请求，这样才算真正省下来。

## 五、两次翻车，比省下的 Token 更说明问题

省调用不算难，难的是出错时系统别装死。这次实验正好翻了两次车。

**第一次，是模型自己把守卫写错了。** R2 的清单里，有一步的完成条件写成输出里要包含 `PASS`。可这一步检查的是构建结果，真实输出是 `BUILD OK`，里面没有 PASS。Harness 逐字对照后判定不通过，当场作废剩下的清单，把控制权交回模型。模型拿到真实输出自查，重跑了一遍校验，确认 `ARTIFACT VERIFY: PASS` 后才收工。

写错的条件没有混过去，代价是多了一次回退，R2 因此比顺利情况多花了一次调用。

**第二次，是我故意制造的。** R3 在集成测试这一步注入了一次真实失败，pytest 以退出码 1 退出。Harness 立刻拦住后面的构建和校验，作废整张清单，把失败结果原样交给模型。模型写了一张新清单重试，集成测试通过后，构建和校验又自动跑完。R3 合计 3 次调用、20,094 Token。

![故意制造一次失败，系统怎么收场](../docs/assets/wx_fault.png)

两次翻车里，能省的调用都省了，该交还给模型的判断一次也没漏。比起 29.6% 这个数字，我更看重这一点。

## 六、账本摊开看

修 bug 用的 16 次调用是三条路线共同的成本，下表只算各自验证阶段的账：

| 路线 | 模型调用 | Token | 省掉的调用 | 审计 |
|---|---|---|---|---|
| R1 每步回调 | 5 | 27,430 | 0 | 通过 |
| R2 决策清单 | 3 | 19,331 | 2 | 通过 |
| R3 故障注入 | 3 | 20,094 | 3 | 通过 |

审计由十项机器检查组成，核心看三件事：执行的参数和清单上写的是否一致，每个环节的记录能否对上，故障之后有没有偷偷继续往下跑。

各家对缓存的计费方式不同，所以这里只比较 Token 总量，不折算成钱。这也只是单个任务的结果，别急着推广。

## 七、下一步：做成 DSH 插件（规划ing）

这套机制真正能落地的位置，是 Agent 运行时的模型调用入口。所有调用都从入口经过，入口先查一遍决策清单，命中就直接执行，没命中就照常交给模型。最先适合改造的，是下一步早就定死的环节，比如跑测试、构建、部署；需要读新信息、做新判断的调用，省不掉，也不该省。

更具体一点，就是把它做成 DeepSeek Harness（DSH）的一个插件。DSH 的口号是 everything is plugin，我最近在 DSH 上做的插件市场（dsh-m）、Copilot授权登录（@inventec/dsh-copilot-auth）和自用Skill bundle（@iasiv5/dsh-skills），都是靠这套插件机制搭起来的。把决策清单拦截器做成插件、装在调用入口上，原生 DSH 的 Token 效率就能直接提上来。

## 写在最后

**模型调用可以省，办法是把已经确定的决策存下来，用真实结果去触发；省不掉的部分，老老实实交回模型。**
